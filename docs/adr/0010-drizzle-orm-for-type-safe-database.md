# ADR 0010: Drizzle ORM for Type-Safe Database Access
Date: 2026-02-15 | Status: Accepted

## Context
CrestDesk's TypeScript services need a database access layer for PostgreSQL that provides:

1. **Type safety**: Database queries should be type-checked at compile time. A query referencing a non-existent column should fail during development, not in production.
2. **Migration management**: Schema changes must be versioned, reviewable, and applied consistently across environments.
3. **Performance**: The ORM should not introduce significant runtime overhead. Real estate transaction queries can be complex (joins across listings, contacts, transactions, documents) and latency-sensitive.
4. **SQL expressiveness**: The abstraction must not prevent writing complex queries. Window functions, CTEs, subqueries, and PostgreSQL-specific features (JSONB, array types, RLS-compatible queries) must be supported.

The Python services (compliance engine, AI services) use SQLAlchemy, which is the established standard in the Python ecosystem and was not reconsidered.

Options evaluated for TypeScript:
1. **Prisma** — popular, good developer experience with Prisma Studio, but generates a query engine binary (~15MB) that runs as a separate process. This adds latency, memory overhead, and deployment complexity. Schema is defined in a custom DSL (`.prisma` files) rather than TypeScript.
2. **TypeORM** — decorator-based, but type safety is incomplete (many `any` types), active record pattern encourages anti-patterns, and the project has had maintenance concerns.
3. **Drizzle ORM** — schema defined in TypeScript, zero runtime overhead (compiles to raw SQL), full TypeScript inference, supports all PostgreSQL features. Migrations generated by `drizzle-kit`.
4. **Kysely** — excellent type-safe query builder, but lacks a built-in migration tool and schema definition layer.

## Decision
Use Drizzle ORM for all TypeScript service database access. Use SQLAlchemy for Python service database access. Both ORMs connect to the same PostgreSQL database.

- Database schema is defined in TypeScript files using Drizzle's `pgTable` builder in `packages/database/schema/`.
- Schema definitions serve as the single source of truth and are shared across all TypeScript services via the monorepo.
- Migrations are generated by `drizzle-kit generate` and applied by `drizzle-kit migrate`. Migration files are SQL, making them reviewable and portable.
- Drizzle's relational query API is used for simple CRUD operations. The SQL-like query builder is used for complex queries requiring joins, subqueries, or PostgreSQL-specific features.
- Every table definition includes `tenant_id` for RLS compatibility (see ADR-0001).
- Python services use SQLAlchemy with models that mirror the Drizzle schema. Schema consistency between the two ORMs is enforced by shared migration files and integration tests.

## Consequences

**Positive:**
- Schema-as-TypeScript-code provides full IDE autocompletion and compile-time type checking for every query. A typo in a column name is caught immediately.
- Zero runtime overhead — Drizzle compiles queries to raw SQL strings at build time. No query engine binary, no extra process, no additional latency.
- Generated SQL migrations are plain SQL files — reviewable in PRs, portable, and compatible with any PostgreSQL migration tool.
- Full PostgreSQL feature support: JSONB operators, array types, window functions, CTEs, `ON CONFLICT` upserts, and custom SQL via `sql` template literal.
- Lightweight dependency — Drizzle adds ~50KB to the bundle vs. Prisma's ~15MB query engine.
- Schema definitions in `packages/database` are shared across all TypeScript services, ensuring consistency.

**Negative:**
- Drizzle is newer than Prisma and TypeORM. The ecosystem (plugins, community resources, Stack Overflow answers) is smaller, though growing rapidly.
- Two ORMs (Drizzle for TypeScript, SQLAlchemy for Python) accessing the same database requires careful coordination. Schema changes must be reflected in both. Integration tests verify consistency.
- Drizzle's relational query API, while powerful, has a learning curve for developers accustomed to Prisma's simpler `findMany` / `include` syntax.
- No equivalent to Prisma Studio (visual database browser). Developers use pgAdmin or DataGrip for visual database interaction.
- Drizzle-kit's migration generation can produce suboptimal migrations for complex schema changes (e.g., column renames are detected as drop + add). Migration files should always be reviewed before applying.
- Team members familiar with Prisma will need to learn Drizzle's API and patterns. Documentation and internal guides are necessary for onboarding.
